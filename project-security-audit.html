Site Security Audit

A Playwright-based security test suite that treats the browser like an attacker would — checking headers, hunting for exposed files, fuzzing for XSS, and attempting clickjacking against this very portfolio site.

← ALL PROJECTS

Concept

Most of the security tooling built for coursework and CTFs runs once and gets thrown away. This one is meant to keep running: it's a small, repeatable Playwright suite pointed at this portfolio site by default, so every deploy gets checked the same way a real audit would — automatically, not by memory.

It defaults to serving only the git-tracked files from this repo through a local static server, which mirrors what GitHub Pages actually publishes (no .git internals, no local-only files) rather than testing the raw working directory. A BASE_URL environment variable can point it at any other target the operator owns or is explicitly authorized to test.

What It Checks

◉

Security Headers

CSP, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, and HSTS on HTTPS origins — audited as soft assertions so one run reports every gap instead of stopping at the first miss.

◎

Exposed Sensitive Files

Hard-asserted checks against .git/config, .env, .htpasswd, backup archives, and a dozen other common misconfiguration paths — a real 200 response here is a finding, not a style nit.

▣

Cookies & Storage

Any cookie the site sets gets checked for Secure/HttpOnly/SameSite; local and session storage get scanned for suspicious key names like token or password.

⚡

Functional Clickjacking Check

Rather than just reading the X-Frame-Options header, it actually embeds the live page in a foreign-origin iframe over CDP and confirms the browser refuses to render it.

●

Reflected & DOM XSS Fuzzing

Fuzzes common query-parameter names with an XSS payload and checks both the raw HTTP response and the rendered DOM, listening for any dialog the payload might trigger.

◎

Mixed Content

On an HTTPS deployment, confirms every subresource is also HTTPS and flags any third-party origin the site talks to that isn't already on an allow-list.

A Real Finding, Not a Green Checkmark

Running the suite against this site's actual deploy target turns up 22 passes and 2 documented failures — GitHub Pages doesn't allow setting custom response headers, so the CSP and clickjacking checks correctly flag that gap every run. That's the intended behavior: an audit tool that always shows green isn't checking anything real. If this site ever moves to a host that supports response headers (Netlify, Cloudflare Pages, Vercel), the fix is a _headers file — documented directly in the suite's README.
